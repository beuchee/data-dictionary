# Reviewing & Proposing on {{forge.name}}

The {{app.name}} uses a {{forge.name}}-based workflow for contributing changes. All content is stored as JSON files in the [{{repository.slug}}]({{repository.url}}) repository.

## Submitting a Review

Open a concept set, go to the **Review** tab, and click **Add Review**. A fullscreen editor opens:

The **Add Review** editor: a header with the **Status** selector (here *Needs Revision*) and the **Submit Review** button, then the Markdown **Editor** on the left and its live **Preview** on the right. Example content typed in the editor:

```markdown
Fetal heart rate should be excluded from this set.

It is recorded at the **maternal level** (in the mother's obstetric record), creating a risk of confusion with the mother's own heart rate.

I suggest moving it to a dedicated concept set to prevent mixing fetal and maternal values during data alignment.
```

Select a **status** (Approved or Needs Revision), write your comments using Markdown in the left editor with a live preview on the right, then click **Submit Review**.

Your review is stored in the current browser session and appears in the Review tab.

## Proposing Changes on {{forge.name}}

You can propose changes on {{forge.name}} in two ways:

- In the **Review tab**, after submitting a review, a **Propose on {{forge.name}}** button appears
- From **any tab**, click **Export** and choose the {{forge.name}} option

In both cases, clicking it:

1. Copies the full updated concept set JSON to your clipboard
2. Opens the {{forge.name}} editor for that file — if you don't have write access, you will be prompted to **fork** the repository into your account
3. Paste the JSON from your clipboard, replacing the file content
4. Commit to a new branch and open a **pull request**

> [!NOTE]
> **No {{forge.name}} Account?**\
> You can still browse and use the dictionary locally. The {{forge.name}} workflow is only needed to contribute changes back to the shared library.

## Build Pipeline

Three Python scripts maintain the data files used by the web application. They are independent steps — in particular, `build.py` does **not** re-resolve concept sets; it reads whatever `concept_sets_resolved/` files already exist.

### resolve.py

Resolves concept set expressions by expanding descendants and mapped concepts using OMOP vocabulary tables. Run it only after editing a concept set’s expression.

```bash
python3 resolve.py --vocab /path/to/ohdsi_vocabularies.duckdb
python3 resolve.py --vocab /path/to/athena_folder      # CSV or Parquet
python3 resolve.py --vocab /path/to/folder --id 10     # resolve one set
```

The `--vocab` source is auto-detected: a DuckDB file (`.duckdb`), or a folder of Athena CSV or Parquet files (CONCEPT, CONCEPT_ANCESTOR, CONCEPT_RELATIONSHIP). Omit `--vocab` to use the `ohdsiVocab` key in `config.local.json`; use `--id` to resolve a single set.

For each concept set, it:

1. Partitions expression items into included and excluded
2. Expands each set with descendants and mapped concepts as configured
3. Computes: included − excluded
4. Writes the resolved set to `concept_sets_resolved/{id}.json` — these pre-computed files allow users to browse the Resolved tab in Concept Set Details without needing to import an OHDSI vocabulary database locally

### snapshot.py

Records, in `concept_sets_versions.json`, the Git commit SHA where each `(id, version)` pair lives, so historical versions pinned by projects can be retrieved later. It is called automatically by `build.py`, so you rarely run it directly. Because the SHA it records must point to a commit that already contains the new version on disk, the workflow is two commits: (1) bump the version field and commit it, (2) run `build.py` (which snapshots), then commit the updated `concept_sets_versions.json`. A concept set with uncommitted changes is skipped (with a warning) — otherwise the recorded SHA would not match the file’s content.

That default mode only sees the version currently on disk, so versions bumped while nobody snapshotted are missed — typically contributions merged through “Propose on {{forge.name}}”, since CI runs `build.py` but never commits the index back. To catch up, walk the Git history:

```bash
python3 snapshot.py --backfill --dry-run
python3 snapshot.py --backfill
```

This reads the `version` field at every commit that touched each concept set and records the commit that *introduced* each version — more accurate than the HEAD approximation, and it recovers intermediate versions the default mode cannot see. Deleted concept sets are included, since a project may still pin one. It only ever *adds*: a pair already indexed keeps its recorded SHA even when the walk finds a different one, because published SHAs are resolved at runtime by the app and repointing one would change a version someone already cited. Those disagreements are reported as divergences (`--show-divergences` lists them) and left untouched. The scan takes a few seconds, so it stays opt-in and is never called by `build.py`.

### build.py

Calls `snapshot.py`, then aggregates all source JSON files into the data files consumed by the static site. No vocabulary database needed.

```bash
python3 build.py
```

Produces:

- `docs/data.json` — Compact JSON for programmatic use
- `docs/data_inline.js` — Same data as `const DATA={...};` for direct script inclusion

> [!NOTE]
> **Full rebuild**\
> After modifying source data files, run both scripts in sequence:\
> `python3 resolve.py --vocab /path/to/vocabularies.duckdb && python3 build.py`\
> The vocabulary source can also be a folder of Athena CSV or Parquet files.

## Claude Code Skills

If you use [Claude Code](https://github.com/anthropics/claude-code) to work on this repository, three skills (slash commands) are available:

- `/resolve-concept-sets` — Runs resolve.py to resolve one or all concept sets using the OMOP vocabulary database
- `/build-catalog` — Runs build.py to regenerate the data files for the static site
- `/describe-concept-set` — Generates a detailed clinical description for a concept set using UMLS, LOINC, and SNOMED vocabulary sources — useful for writing the Comments tab content

These automate the build pipeline and assist with documentation.
