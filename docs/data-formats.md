# Data formats and content conventions

The JSON files at the repo root are the **source of truth** and must stay readable by v1 (`legacy/`), v2 (`apps/`) and Linkr (`lib/data-dictionary/` there). Any format change has to keep all three working.

## Files

| Path | Content |
|---|---|
| `concept_sets/{id}.json` | Concept set definition (OHDSI expression + INDICATE metadata) |
| `concept_sets_resolved/{id}.json` | Resolved concepts, generated by `resolve.py` but **committed** |
| `projects/{id}.json` | Project: translations + `groups[]` of pinned `{id, version}` concept sets |
| `units/recommended_units.json` | Recommended unit per concept |
| `units/unit_conversions.json` | Unit conversion factors (optional affine `offset`) |
| `mapping_recommendations/mapping_recommendations.json` | `{translations: {en: {content}, …}}`, Markdown |
| `config.json` | Per-instance settings: title, languages, repository, organization, customVocabulary, branding, tabs, access |
| `branding/` | Logo and favicon uploaded from v2's Branding settings (`logo.<ext>`, `favicon.<ext>`); see below |
| `id_counters.json` | Next ids. Only `build.py` writes it (auto-corrects) |
| `concept_sets_versions.json` | `{id: {version: commitSha}}`. Only `snapshot.py` writes it |

On-disk format: 2-space indent, UTF-8 not escaped (`json.dumps(indent=2, ensure_ascii=False)`), trailing newline — except `concept_sets_resolved/*.json`, which `resolve.py` writes without one. A file read and rewritten unchanged must be byte-identical; `packages/dictionary-format` implements this in TS and Python and tests it on every content file.

- Number lexemes are preserved: `units/unit_conversions.json` holds factors like `1.0` that plain `JSON.stringify` would rewrite as `1`. Never save content with bare `JSON.stringify`; use the format package's `serialize`.
- `config.json` is hand-formatted (inline arrays) and listed as the only non-canonical file in `packages/dictionary-format/fixtures/non-canonical.json`.
- A `config.json` written by v2 (Branding settings, setup wizard) comes out canonical: the hand-formatted inline `languages` array becomes one item per line. Accepted: the file stays valid for v1, the scripts and Linkr.
- Real files tolerate some legacy values the schemas accept: `standardConcept: ""`, `validStartDate`/`validEndDate` as `YYYYMMDD` or empty, reviews without `status`.

## Concept set schema

The canonical, annotated schema is [`concept_set.example.json`](../concept_set.example.json); follow its field order and structure exactly. Project schema: read any `projects/*.json`. Resolved schema: read any `concept_sets_resolved/*.json`.

Fields that the example does not make obvious:

- **Root `name`/`description` mirror English**: `name` = `metadata.translations.en.name`, `description` = `metadata.translations.en.shortDescription`. Translations are the source of truth; editors keep the root in sync.
- **`shortDescription`** is the one-line plain-text table summary (no Markdown). **`longDescription`** is the full Markdown shown in the detail view. Both are per language.
- **No cross-language fallback** anywhere: a missing translation shows nothing (intentional, to encourage filling it).

### Identity and provenance (cross-repo sharing)

Concept sets are shared between separate dictionary repos (different organizations, different Git hosts). Four metadata fields carry identity and provenance. The import flow is in `legacy/concept-sets.js` (`importOneCandidate`).

- **`metadata.uniqueId`**: the **lineage** id (UUID), the same across versions *and* across forks. Generated once at creation, **kept unchanged on import**. Unique within a repo: importing an existing one either skips it (same `version`) or overwrites the local copy (different `version`); never duplicate it.
- **`metadata.organization`**: `{created, current}`, each `{name, url}`. `created` is the authoring org (immutable). `current` is the org owning the **latest** content, set to *my* org on every edit and on import. The legacy flat `{name, url}` is normalized to both at read time.
- **`metadata.sourceRepo`**: URL of the repo currently maintaining the object. **Refreshed on every edit** and on import, so provenance survives even a manual copy-paste.
- **`metadata.origin`**: provenance of *this* copy, written **once at import** and then **frozen** (so an A→B→C chain doesn't telescope). `null` for sets created here. Shape: `{uniqueId, repo, version, commit, organization, importedDate}`. There is deliberately no content hash: `repo` + `version` + `commit` is enough to fetch the source back.

## Conventions

- **Multilingual is language-first**: `{en: {...}, fr: {...}}` keyed by BCP 47 code, camelCase fields. Applies to concept sets (`metadata.translations`), projects (`translations`), groups (`groups[].translations`), mapping recommendations. A new translatable field goes **inside** the per-language object, never as a field-first `{en, fr}` object (rationale: issue #17).
- **OMOP concept metadata comes from the vocabulary, never hard-coded.** For `expression.items[].concept`, read `standard_concept`, `domain_id`, `vocabulary_id`, `concept_class_id`, `concept_code`, `concept_name`, `valid_start_date`, `valid_end_date`, `invalid_reason` from `concept`.
- **`standardConcept` drives the badge**, not `standardConceptCaption` (informational). Values: `'S'` Standard, `'C'` Classification (valid hierarchy anchor with `includeDescendants`), `null` Non-standard. Writing `standardConcept: null` + caption `"Classification"` is a common mistake: the badge then shows "Non-standard". **Don't use non-standard concepts directly**; prefer the standard concept they `Maps to`.
- **`reviewStatus`** is exactly one of these snake_case slugs: `draft`, `pending_review`, `approved`, `needs_revision`, `deprecated`. Never the human label: a spaced value breaks the status filter and badge.
- **Categories** come from `metadata.translations.{lang}.category` / `subcategory`. **Versioning** is semantic `version`. **Athena links**: `https://athena.ohdsi.org/search-terms/terms/{conceptId}`.
- **IDs** are monotonic and never reused; increment `id_counters.json` when creating a file by hand (`build.py` corrects it if too low).
- **Custom concepts** use the `customVocabulary` of `config.json` and ids from 2 000 000 000 upwards.

## Recommended units (lab/biology)

`units/recommended_units.json` follows the **`EXAMPLE_UCUM_UNITS`** column of the official LOINC table (`LoincTable/Loinc.csv`, https://loinc.org/downloads/), matched by the concept's LOINC `concept_code`. If several units are listed, pick the one matching the property (e.g. `umol/L` for a Moles/volume LOINC). Any deviation must be justified in the concept set description. **Non-lab** concepts (vitals, scales, doses): methodology not defined yet.

## Branding images

`config.json` → `branding.logo` / `branding.favicon` are paths **relative to the site root**, as v1 reads them.

- **v1's images** (`logo.png`, `favicon.png`) live in `legacy/`, which is v1's site root.
- **Images uploaded from v2** (Settings → Branding, setup wizard) are committed to **`branding/` at the repository root** as `branding/logo.<ext>` / `branding/favicon.<ext>` (type sniffed from the bytes: PNG, JPEG, GIF, WebP, ICO, SVG without scripts; logo ≤ 1 MB, favicon ≤ 256 KB), and config.json names that path (`"logo": "branding/logo.png"`). A replaced `branding/` image is deleted in the same commit.
- Who serves them: `build.py` copies `branding/` into `legacy/branding/` (gitignored, like the rest of its output), so v1's Pages site resolves `branding/logo.png`; v2's vite plugin serves and emits `branding/…` from the repo root and anything else from `legacy/`; in server mode the web app loads the content repository's current images from `GET /api/v1/instance/branding/{logo|favicon}` (no rebuild after a branding commit).
- In a `config` draft the images travel under a reserved top-level key, `"$assets": {"logo": {"filename", "base64"}, "favicon": …}`, checked when the draft is saved and again at submit, and never written to config.json (docs/design/drafts-and-proposals.md). Static mode cannot upload images (the forge's edit page takes one text file): add them to `branding/` by hand.
